## Robustness (аналіз API 2026-07-27)

- [x] 🔴 **Станція обслуговує лише ОДНЕ HTTP-з'єднання і забирає його назад — серіалізувати всі запити**
  - **Де:** `charger/base.py` — усі запити до пристрою йдуть через `_request` без жодної
    серіалізації.
  - **Чому:** у станції один слот сесії, і при появі другого з'єднання вона не ставить його в чергу і
    не відмовляє, а **закриває вже наявну сесію**. Додатково: немає таймауту простою і вона ніколи не
    надсилає `Connection: close`.
  - **Наслідки:** (а) паралельні запити тут не просто повільні, а руйнівні — з боку клієнта це
    раптовий FIN/RST, тобто `ServerDisconnectedError`, `ConnectionResetError` або обрізане тіло;
    (б) сокет із пулу keep-alive живе до першого чужого звернення, після чого тихо вмирає, і падає
    **наступний** запит на ньому; (в) будь-хто, хто відкрив веб-інтерфейс зарядки, опитує її раз на
    секунду і тим самим вибиває наш сокет. Це найімовірніша першопричина таймаутів і обривів, за
    якими проєкт давно ходить.
  - **Фікс:** один `asyncio.Lock` у `BaseCharger` навколо кожного запиту до пристрою, щоб запис
    ніколи не перетинався з опитом або іншим записом.
  - **НЕ:** розраховувати на `PARALLEL_UPDATES` — наші сутності читають з координатора, записи він не
    гейтить; тримати лок під час `async_request_refresh()` після запису — рефреш заклінить об запис.
  - **Далі окремо (не в цьому ж фіксі):** надсилати `Connection: close` замість переюзу сокета з
    пулу; один retry через 1–2 с лише на транспортних помилках.
  - **Перевірка:** два одночасних сервісних виклики плюс рефреш координатора дають три послідовних
    HTTP-запити, які не перетинаються.

    `unavailable`.

    ці дані беруться з об'єкта сутності (`homeassistant/helpers/restore_state.py:178`, **джерело —

    публічний API), а не зі стану, тож недоступність їх не стирає. **Разом із цим — одноразова

    стану, як зараз.

    без міграційного зчиту фікс **гарантовано відтворює власний баг рівно один раз у кожного
    користувача**, посеред доби, на першому рестарті після апгрейду.

    коректна.

    але з `extra_data`, і зберігає `_baseline`/`_accumulated`; добове значення після перезапуску

## Bugs (знайдено при код-рев'ю 2026-07-17)

- [x] **Binary sensor `ground` інвертований** — `device_class=SAFETY` означає on=Unsafe, а код вмикав сенсор при `ground == 1` (`binary_sensor.py`, `_ACTIVE_VALUE`). Підтверджено на живому пристрої 2026-07-27 (прошивка R3.05.4/R3.05.5): `ground=1` і в standby, і під час зарядки — робочий стан. Фікс: `raw_on = (ground == 0)` (немає землі → небезпечно).
- [x] **V1 `systemTime` інтерпретується в таймзоні ОС, а не HA** — `charger/v1.py` парсив time-only `"HH:MM:SS"` через `datetime.now().astimezone()` (локальна tz процесу/ОС), тож `TimeDriftSensor` показував хибний зсув, коли контейнер HA в UTC, а конфіг — інша зона. Фікс: charger повертає **naive** datetime (тільки wall-clock), а `coordinator._async_update_data` локалізує його через `dt_util.now()` у поточну HA-tz (tz-aware V2-час проходить без змін). Прибрано `_UTCNowDatetime`-кістяк зі snapshot-тесту (снапшот пінить HA-tz=UTC → drift той самий `-38050`); golden/transform V1 тепер очікують naive; додано 2 координаторних тести (naive→HA-tz, aware passthrough).
- [x] **Binary sensor `groundCtrl` мертвий і з неправильним класом** — код чекав `groundCtrl == 2`, але API-дока каже `0/1 = Ground control enable`. Підтверджено на живому пристрої 2026-07-27: `groundCtrl` 0→1 рівно в момент, коли на дисплеї станції з'явилось «PE control On» (вручну увімкнули) — це конфіг-прапорець, не аварія. Фікс: порівняння з `1`, прибрано `SAFETY`, додано `entity_category=DIAGNOSTIC`. Довгостроково лишається кандидатом на switch (якщо `/pageEvent` дозволяє писати). **(Уточнено 2026-07-27: писати його технічно можна, але користувацького switch робити НЕ треба — це сервісний перемикач, який відключає контроль захисного заземлення. Лишається read-only діагностикою; деталі — у блоці про записувані параметри в Backlog.)**
- [x] **Repair issue спільний для всіх entries** — `coordinator.py` створює/видаляє issue з фіксованим id `"device_error"`. З двома зарядками: перша в помилці → issue створено; друга опитується успішно → `async_delete_issue` стирає issue першої. Фікс: `issue_id=f"device_error_{entry_id}"` + додати ім'я пристрою в translation placeholders.
- [x] **Витік aiohttp-сесії при невдалому старті інтеграції** (знято класово рефакторингом R2 — спільна сесія HA) — `async_setup_entry`: `ChargerV*` створюється до `async_config_entry_first_refresh()`; якщо перший рефреш падає (зарядка офлайн при старті HA) → `ConfigEntryNotReady`, `charger.close()` ніхто не викликає, а `ClientSession` уже створена всередині `_request`. HA ретраїть setup нескінченно → нова незакрита сесія на кожен ретрай («Unclosed client session» у логах). Фікс: try/except навколо first_refresh із `await charger.close()` перед re-raise; правильніше — перейти на спільну `async_get_clientsession(hass)` (див. рефакторинг нижче), тоді проблема зникає класом.
- [x] **`session_ended` реплеїться після офлайн-розриву** — `_prev_state` у координаторі не скидається при невдалих оновленнях: зарядка зникла з мережі під час Charging, з'явилась через годину в Standby → летить `eveus_session_ended` зі старими live-цифрами і `ended_at=now`. Це суперечить власній design-нотатці («НЕ реплеїти переходи, що сталися поки зарядка/HA були офлайн»). Фікс: у except-гілках скидати `_prev_state = None` (перший успішний poll після розриву стане новою базою без події) — або фіксувати тривалість розриву і глушити подію після N хвилин офлайну.
